## Order of operations

The order matters and `D-0044` is right about why: the password gates the
endpoint that serves the key.

### Step 1 — `AUTH_PASSWORD`

Rotate first. It gates `/api/pipeline-logs`, which is where the 14 copies are
readable. Until this moves, the FRED key is effectively public because
`F-0009` put the current password in public git history.

    flyctl secrets set AUTH_PASSWORD=<new> -a sentinel-holy-rain-4562

Then update the local `.env` to match, or every verification script in this
repo stops working — including the ones in step 5.

**Rotate `AUTH_USERNAME` at the same time, which `D-0044` does not mention.**
The current username is the application's own name, which is derivable from the
public Fly hostname in about one second. `F-0009` put the password in public
git history; together that is not a credential pair, it is two public strings.
Rotating only the password leaves half of it guessable by anyone who can read
the repository — and the repository is public by decision.

    flyctl secrets set AUTH_USERNAME=<new> -a sentinel-holy-rain-4562

Set both in one `flyctl secrets set` invocation if possible: two separate calls
means two machine restarts and a window where the pair is mismatched.

### Step 2 — `FRED_API_KEY`

Rotate second. **This is the fix.** It neutralises all 14 stored copies the
moment it lands; the scrub in step 3 is hygiene afterwards and nothing depends
on it.

    flyctl secrets set FRED_API_KEY=<new> -a sentinel-holy-rain-4562

New key from https://fredaccount.stlouisfed.org/apikeys — revoke the old one
there, do not merely replace it here.

precondition — a completed backup plus a recovery credential held outside any
